A factual record of what the v1.1 implementation candidate contains, what was
**verified**, and what is deliberately absent. It exists so that "done" is never
implied by silence. Nothing here is a release claim: there is no tag, no publish,
and no HARDENED capability.

### The six failures are pre-existing, and that is measured, not assumed

`probe: M8 promotion`, `probe: M9 authority guard`,
`probe: pre-1.0 execution-environment authority`,
`probe: pre-1.0 human-acceptance`, `probe: master-pass mutation battery`,
`probe: acceptance growth`.

Each was run at `08283a5` — the commit the v1.1 work started from — and fails
there with the same names, codes and expected/actual values. They are host-bound
(git resolving outside the trusted dirs; PTY-driven acceptance). They are recorded
here for the later validation phase. **Do not green them by relaxing an
assertion.** The oracle stays red until they are genuinely fixed.

**One is now fixed** (`pre10-env-authority`, commit `1abe0b2`), leaving five. The

### First one diagnosed, precisely (`pre10-env-authority`)

The probe asserts that every executed file lies inside Canary's own trusted set,
and it builds that set by **hardcoding a mirror** of `trustedDirs()` from
`apps/cli/src/onboarding.ts` (`pre10-env-authority.mjs:27-35`). The product's
`gitExe()` resolves git from fixed literal candidates — which is deliberate, so a
PATH shim can never become git — and on this host that is
`C:\Program Files\Git\cmd\git.exe`, a directory **outside** the mirrored set. So
the promotion step's `exec.file` is reported as untrusted.

Two things are wrong, and they are fixable in this order:

1. **The mirror should not exist.** `trustedDirs()` is not exported, so the probe
   copies it; any future change to the product's trust set silently desynchronises
   the assertion that is supposed to police it. Export the set (or a
   `trustedDirsFor(platform)` helper) and have the probe import it, so there is one
   source of truth.
2. **The set is incomplete for what Canary actually executes.** `gitExe()`'s
   literal candidates should be part of the trusted set by construction — the
   directories it will execute git from are, by definition, directories Canary
   trusts. Add them at the same place the candidates are defined rather than as a
   second list.

Neither change should widen program resolution: the fix is to make the *declared*
trust set match the set of directories Canary executes from, then have the probe
read that declaration instead of paraphrasing it.

**Fixed in `1abe0b2`.** The git candidates became a named helper whose
directories are part of the (now exported) `trustedDirs()`, and the probe imports
that declaration rather than mirroring it. `pre10-env-authority` reports ALL PASS,
including its honest controls — which is the check that the fix did not simply
delete the assertion.

### Second one diagnosed: `m9-authority`, and it is narrower than it looks

The failing assertion is the cross-case hygiene check
(`m9-authority.mjs:354-360`): for the `base-refmove` repo the **last** candidate
bundle must have status `blocked` (the M9 mandate after authority drift), and it
reads `fail`.

What is *not* broken: the scenario that exercises the guarantee itself passes. The
probe confirms the sealed step moved the base branch, the mandate names the ref
with both edge tokens equal to the sealed and live HEADs, the guard "witnessed the
move; it did not (cannot) stop it" (detection is the stated ceiling), `isolate
--promote` refuses with exit 2 naming the quarantine, it never reads the moved ref
as `ALREADY APPLIED`, and **no promotion bundle is written**. So the security
property holds; what fails is the *label on the last artifact written afterwards*.

Next step to confirm (not yet done): read the promote-under-quarantine refusal path
in `apps/cli/src/candidate.ts` and see which bundle status it writes. The
hypothesis is that a refusal taken because the base is quarantined records `fail`
(the plan's outcome) instead of `blocked` (the mandate), which makes the probe's
"last verdict must be the mandate" assertion fail even though every guard fired.
If that is what it is, the fix is a label/consistency fix in one refusal path — not
a change to any gate — and it must be proven by re-running this probe, not by
editing the assertion.

### Third and fourth: `m8-promotion` is the SAME root cause, and it is now identified

Running `m8-promotion` with full output shows both its failures, and they are one
defect — the same precedence defect as `m9-authority`:

1. *"mid-plan commit attack: candidate HEAD moved during verification → REFUSED
   (sandwich), honest recovery on re-run"* expects the output to say
   `/changed during verification/`, but the run reports **`CANDIDATE FAIL — 1/1
   step(s) not green; the trusted base was not touched.`**
2. *"cross-case hygiene: … attempted repos land exactly once"* expects one
   promotion bundle and finds zero — a second-order effect of (1), because the
   repo never reaches the promote path.

**The defect**: when the sealed plan fails, verification returns the plan's verdict
before the identity/authority sandwich is reported, so a change witnessed *inside
the verification window* is presented as "your tests failed" instead of "your
candidate moved underneath me". That is not a security hole — a plan failure blocks
promotion anyway — but it is a **reporting** failure with real cost: it sends an
agent to fix tests when the actual event is an integrity violation, and it hides
the tamper from the human reading the evidence. The doctrine already requires the
opposite for the passing case (`m9-authority` forces BLOCKED on drift); the failing
case must be symmetric.

**The fix is one precedence change** in the verification path of
`apps/cli/src/candidate.ts`: evaluate the post-window identity/authority checks
before finalizing the plan's outcome, so a witnessed mid-window change (or
authority drift) yields its own refusal and message regardless of whether the steps
passed. It touches no gate's strength — every guard already fires; the question is
only which one gets to speak.

So of the six reds: **one fixed, two explained by a single identified defect, three
undiagnosed** (`pre10-acceptance`, `master-pass-mutations`, `f3-acceptance-growth`
— the last two cascade: `master-pass-mutations` aborts because the `pre10`
baseline arm is red).

**Attempted, and it is NOT a simple precedence move** (experiment reverted; the
tree is green at `fd08b48`). Moving the sandwich ahead of the plan's verdict was
implemented two ways and re-run:

- *First attempt* — compare HEAD/tree before and after the window: the probe still
  reported `CANDIDATE FAIL`, because this attack makes the candidate **dirty**
  inside the window rather than moving its HEAD.
- *Second attempt* — also treat "was clean, is now dirty" as a mid-window change:
  the refusal then fires and the message assertion **passes**, but the probe's next
  step fails: *"re-promote of the stable head failed: expected 0, actual 2"*. The
  refusal left state that the honest recovery re-promote trips over — most likely
  the refusal artifact itself (an authority/refusal event) being read by the next
  run as a reason to refuse again.

So the real defect is two-part: the sandwich must speak before the plan's verdict,
**and** its refusal must leave the candidate recoverable by re-running after the
worker commits (only *authority* tampering earns a quarantine; a candidate that
moved under the verifier does not). That is exactly the kind of change that must be
made with the whole `candidate.ts` verify/refuse/quarantine path in view and proven
by re-running `m8-promotion` *and* `m9-authority` — not by iterating against one
assertion at a time, which is what the two attempts here demonstrate.

**Where to look first, and why.** The M9 sandwich takes a *pre-window* fingerprint
(`candidate.ts:505`, "fingerprint the authority bytes AND the evidence tree") and
compares it after the run. An early return inserted before that post-window
comparison **closes nothing** — if the window's state (the fingerprints, or a
"window open" marker) is only retired by the post-window check, then every early
refusal leaves it behind, and the NEXT invocation reads the stale window as reason
to refuse. That is the most likely mechanism behind the observed "re-promote of the
stable head failed: expected 0, actual 2", and it explains why the message
assertion passed while the recovery assertion broke. So: before touching the
precedence again, establish whether the post-window authority comparison performs
bookkeeping that every refusal path must also perform (or must be made idempotent /
re-entrant). If it does, the fix is to close the window on **every** exit from
`verifyCandidate` — a `finally`-shaped change — rather than to reorder the verdicts.

**That hypothesis is REFUTED** (checked in `candidate.ts`, not guessed): the
pre-window snapshot is a plain in-memory value (`const preAuth =
snapshotAuthority(authority)`, line 516), the post-window comparison is
`authorityDrift(preAuth, authority)` plus the seal re-check, and the ONLY persistent
side effect is `stampQuarantine` inside `authorityBlock` (line 376), which runs
solely when a *during/after* catch is actually found. An early `blocked(...)` return
therefore leaves no window state behind, and no quarantine.

So the recovery failure has a different cause, and the next thing to read is the
probe's own recovery sequence (`m8-promotion.mjs`, the `midplan` scenario) rather
than more of `candidate.ts`: the question is whether the scenario's step moves the
candidate on *every* run — in which case an inserted check correctly refuses again
on the recovery run while the probe expects that run to be judged on its own
merits — or whether the probe cleans the candidate and a fresh run should proceed.
The answer decides whether the fix belongs in the precedence at all, or in what the
probe's recovery is entitled to expect.

**Answered: the probe's expectation is coherent, and the fault is in our refusal.**
`m8-promotion.mjs:260-283` builds a candidate whose sealed test step, *if*
`marker.txt` contains `FAIL`, rewrites it to `ok` and commits inside the window —
once. The scenario asserts exactly two things: run 1 is refused with
`/changed during verification/`, and run 2 (`isolate --promote`) **succeeds** on the
same committed state, because the step's guard means it does not commit again. That
is a correct, honest recovery contract: the tamper is named once, and the worker's
own commit is then promotable. So the fix does belong in the refusal — it must
report the sandwich **and** leave the candidate exactly as promotable as it was.
An early `blocked(...)` return evidently changes something run 2 depends on; find
out what by reading run 2's own output (see the method note below) rather than by
reordering the verdicts again.

**Method note: the diagnostic was hidden by filtering.** The probe prints
`r2.stdout` inside its own failure message, and the runs in this record filtered
output through a pattern list (`FAIL|expected|actual|…`) that cut that block — which
is why "expected 0, actual 2" arrived without the reason run 2 refused. Run the
probe and read the **whole** failure block before changing anything; the answer is
very likely already in it.

### Fixed during v1.1

`probe: architecture-metrics` asserted that `canary status` performs zero writes,
and it was right to: the sealed-copy level report called the *writing* probe, so a
command documented as zero-write made three write syscalls (invisible on disk,
because the probe file is created and unlinked). `status`, `result` and `agents`
now use a read-only level assessment; the writing measurement stays where writing
is already part of the job.

## Delivered

- **Projects**: Python, Rust and Go adapters behind the one `ProjectAdapter`
  contract, with discovery that never invents a check (a tool named in a comment
  or a description is prose), deterministic polyglot composition at a repository
  root, and toolchains **pinned to absolute paths at setup** so PATH is never
  consulted during verification.
- **Agents**: an honest capability table (`GATED` vs `ADVISORY`) surfaced by
  `canary agents`; `canary agents install codex` writes a marked, removable
  `AGENTS.md` block; `AGENTS.md` gives every harness the repository rules.
- **Machine interface**: `canary result --json` plus a global `--json` where
  stdout is exactly one versioned envelope, prose moves to stderr, and exit codes
  and status words are identical with and without the flag.
- **Workflow**: `canary work` / `canary finish` orchestrate the existing
  primitives (register + isolate; verify + promote) without re-implementing a
  gate, and never close a subjective duty.
- **Adaptive fast path**: a project may declare which paths each check depends on
  (`canary.paths`); setup **validates and seals** that declaration with the plan,
  and `doctor --fast` (opt-in) leaves out only the checks whose declared paths the
  change provably missed — printing every skip with its reason and carrying them
  in the JSON envelope as `skipped`. Undeclared checks always run, an empty change
  set runs everything, and `finish`/promotion never take the flag.
- **Cost**: model-neutral metrics (off by default, fail-open, no free text or
  paths recorded).
- **Trust**: the Astra P0 kernel merged in — lossless authority signing, a
  compare-and-set sealed store, the authorization kernel, and the platform
  contracts — with the mutation probe as its behavioural specification.
- **Adoption**: `CONTRIBUTING.md`, `AGENTS.md`, `CHANGELOG.md`, root
  `SECURITY.md`, issue/PR templates, Dependabot, `.editorconfig`, a machine-
  readable `schemas/spec.schema.json`, a CI restructure (the proof job is no
  longer skipped behind a red matrix) and a tag-driven release workflow.

## Deliberately NOT delivered

**1. The provider chain — so `HARDENED` does not exist.** No installed broker
service, authenticated IPC, immutable source import, sandbox, supervisor, review
path, promoter or enforced network policy. The contracts exist; nothing implements
them. The CLI's real paths still run on the LOCAL sealed store, and the same uid
can replace the store, its keypair and its ledger together. See
[`TRUST-ARCHITECTURE.md`](TRUST-ARCHITECTURE.md).

**2. Fast-path drift reporting — CLOSED** (`f7d8673`). A live edit to
`canary.paths` is now compared against the seal and reported as drift, and drifted
authority makes `doctor` refuse *before executing anything*, so a widened
declaration grants neither a skip nor a run. Kept here as a record rather than a
gap.

**3. Runner-observation adapters.** Strong labels (`PASS`,
`CONFIRMED_REGRESSION`, `FLAKY`, `PRE_EXISTING_FAILURE`) still require a VALID
execution observation, and the pin table covers exactly one real runner release
(mocha 10.8.2). jest, vitest, ava and pytest projects therefore cannot reach a
strong label — rule 14 sends them to `INCONCLUSIVE`. This is stated in
`EXECUTION-AUTHORITY.md`; adding a runner means adding a pin **and** its reviewed
manifest.

**4. Nested ecosystem scopes.** Discovery is root-scoped by default so that an
`archive/` or `examples/` directory cannot silently add checks to the project that
contains it. Subdirectory scopes need an explicit declaration.

**5. Node-free distribution.** Canary is a Node.js program. A Python or Rust
*project* needs no `package.json`, but running Canary does need Node 22+. There is
still no `npm install canary` or standalone binary.

**6. An MCP server.** Agents integrate through `AGENTS.md` plus the machine-
readable protocol; there is no MCP entry point.
