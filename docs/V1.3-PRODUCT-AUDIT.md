# Canary v1.3 — product audit

**Status:** Phase A deliverable, with the first implementation slice landed and verified.
**Audited tree:** `main` @ `b7e2cae` (v1.2.0), clean worktree.
**Method:** every claim below is either (a) an executed measurement with the command or probe that
produced it, or (b) a `path:line` reading. Interpretations are labelled. Where a number does not
support the conclusion people would like to draw from it, that is stated in the same paragraph.

Three read-only audits were run against the v1.2 tree and are the source of the UX, token and
integration sections: the user-facing surface audit, the token-shape audit, and the agent-integration /
Cursor capability audit. The journey itself was measured with a new probe,
`tooling/probes/v13-journey-baseline.mjs`, which prints `PASS`/`FAIL` for the invariants this slice
establishes and `OPEN` for the gaps it deliberately does not close.

## CURRENT USER JOURNEY

Two disjoint journeys exist today, and **neither one is the journey the product promises.**

### A. The everyday journey (a completion gate that does not confine anything)

1. `npm install -g ./canary-rn-cli-1.2.0.tgz` (Node ≥ 22).
2. `cd repo && canary setup --yes`. Canary detects the project, infers a verification plan from checks
   the project *already declares*, seals it, installs a Claude Code `Stop` hook into
   `.claude/settings.json`, and smoke-runs the plan. Measured output on a fresh Node repo: plan
   `✓ tests: npm run test`, smoke test exit 0, verdict `READY`, exit 0.
3. The user asks their coding agent to do something. **The agent edits files and runs shell with its
   own native tools.** There is no `PreToolUse` hook anywhere in the product; every edit happens before
   Canary is consulted.
4. The agent says it is done → the `Stop` hook runs `canary checkpoint` → the sealed plan runs → on
   failure the completion is **blocked once** (`stop_hook_active` then allows with a message).

So the default path is a *detector at the end*, not a guardian. Measured consequence: a normal agent
edits the base directly and `canary doctor` answers
`READY — wiring verified; the checks just ran and passed, and no proof obligation is open.`

### B. The proven journey (real authority, all of it manual)

5. `canary task "<intent>" --requirement "<each part>"` — the requirement list is human knowledge.
6. If any requirement has no sealed check: `canary bind <script> --requirement "<exact text>" --reseal`.
   **This is an OPERATOR act**; an agent may not perform it.
7. `canary work <name> "<intent>"` → prints a candidate directory → work only there → `git commit`
   there → `canary finish <name>`.
8. Subjective duties: `canary accept <name>`, typed in a real terminal.
9. Cleanup: `canary isolate --remove <name>`.

There are **20 commands** in the CLI. Two interactive prompts exist in the whole product (the setup
smoke-test `[Y/n]`, and the acceptance name-typing). There is **no per-command help**: `canary setup
--help` *runs setup and writes*, `canary doctor --help` *runs the checks*; only `mcp --help` behaves.

### CORRECTION — a claim in the first draft of this audit was wrong, and measuring it changed the plan

The first draft recorded, as friction #5 and as the probe's `OPEN` finding, that *"an agent that edits
the base directly is told `READY` while the candidate route can refuse"* — i.e. that the default path
accepts a green suite as done. **The observation was accurate; the inference was not.** Section F of
the journey probe measures the completion gate directly, by invoking `canary checkpoint` exactly as
the harness does, and the result is the opposite of the inference:

| everyday case (direct edit, no candidate) | measured verdict |
|---|---|
| behaviour change **with** a check the sealed plan can discriminate | `ALLOW` (silence — the documented "nothing needed" signal) |
| behaviour change **no declared check can see** | **`BLOCK`: "Canary blocked completion: NOT PROVEN — the sealed checks pass on the base commit too, so they carry no evidence about this change (greeting.cjs)"** |
| docs-only change (no behaviour moved) | `ALLOW` |

The earlier fixture had changed **both** the source and the test, so the plan genuinely discriminated
the change — the `READY` was *earned*. `discriminationObligation` (`onboarding.ts:1315`) is applied
unconditionally on the checkpoint path (`onboarding.ts:2817`), so the product's most important
invariant — *a green suite that cannot tell the change from the base proves nothing about it* — **is
already enforced on the path every ordinary user is on.**

Two consequences, both of which change what v1.3 should build:

1. **The everyday path is closer to "just works" than the first draft claimed.** `setup --yes` once,
   then use your agent normally, and an undiscriminated change is refused. The remaining everyday gap
   is the missing *lifecycle* (no isolation, no frozen task authority, no promotion of exact verified
   bytes) — a product gap, not a trust hole, and largely inapplicable to a user editing their own
   repository.
2. **The highest-leverage remaining work is therefore NOT closing a false-acceptance hole.** It is
   moving the *timing*: today the gate speaks only at the end, so the agent cannot ask "am I done?"
   mid-flight and instead runs its own verification campaign (~36 of 57 execs). Giving the agent
   Canary's verdict **as a tool, wired by `setup`**, is what serves criteria (3) and (4) together.

The probe now asserts all three cases (`F1`/`F2`/`F3`) so the corrected reading is the one under test,
and records the narrower lifecycle gap as the sole `OPEN` finding.

## TOP TOKEN COST SOURCES

Measured from the retained transport logs of the v1.2 pilot (Canary arm 585,337 tokens on
`stateful-replay`; plain arm 212,777).

**The shape, first, because it is the whole story:** plain pays a large *constant* per turn
(~12.2–12.6 K, its own system prompt and six native tool schemas) and adds almost nothing — its cost is
linear in turns. The Canary arm pays a tiny constant (~600) but adds **~2,350 tokens of its own
content per turn**, which every later turn re-reads — its cost is quadratic. That is why the same arm
wins by 84 % on a 6-turn task and loses by 175 % on a 22-turn one.

| # | Source | Size | Mechanism |
|---|---|---|---|
| 1 | **The model's own output, re-read on every later turn** | output 39,351 tokens (4.9× plain's 8,002); × ~10.5 re-reads ≈ **413 K ≈ 70 %** of the run | The confined tool has **no edit primitive** — the schema is exactly `list\|read\|write\|exec` (`worker-tools.ts:31-33`). Every change re-emits a **whole file body inside the assistant message**, which then lives in history forever. Measured: `src/api.js` (979 B on disk) written **9×**. |
| 2 | **Tool-result payloads, appended and re-read the same way** | 49,329 B over 21 results ≈ **22 %** | `exec` returns the whole stdout *and* stderr, `read` the whole file — no truncation anywhere (`production-tool.cjs:31-44`) — plus ~323 B of `observation` boilerplate on **every** call. The largest results are the model's *own* test runs (max 8,739 B), not fixture files. |
| 3 | **Turn count as the multiplier** | 22 turns vs plain's 18; **45 turns / 917,504 tokens** before the batching change | Each turn pays the entire accumulated context. Turns grow when the model runs things — and the model runs things because it cannot otherwise know it is done. |
| 4 | **Fixed per-request overhead** | Canary ≈ 600 × 22 ≈ **2 %** — negligible. Plain ≈ 12.2–12.6 K × 18 ≈ **210 K of its 212,777** | Plain's cost is almost entirely its own base context. This is the constant the Canary shape trades away. |

**Three things the recorded data does not support**, stated here because they are the claims most
likely to be repeated:

- **The +54.4 % is not a property of "Canary".** n = 1 per Canary cell; the arms differ in tool
  surface, system prompt (`--bare`), memory (`--setting-sources ''`), prompt text and day; the plain
  arm is a *recorded* run, not a paired one; `stateful-replay` is 92.5 % of the Canary total.
- **In money it is worse than in tokens: +110.6 %**, not +54.4 % (recorded `costUsd` $0.8414 →
  $1.7723), because cache reads bill at a fraction of output and the Canary arm is output-heavy
  (43,338 vs 12,848 output tokens).
- **"Cache-read is 83 % waste" is wrong** — plain's cache-read share is *higher* (85.4 %). Only
  `turns × content` is actionable.

## WHAT CAN BE MADE AUTOMATIC SAFELY

The test applied to each item: *can Canary establish this objectively from the repository or from the
human's own words, without inventing a duty or dropping one?*

**Safe, and now automatic:**

- **Project, package manager and verification-plan discovery.** Already fully automatic: lockfile →
  pm; `test`/`typecheck`/`build`/`bench`/`e2e` script names → plan kinds; Python/Rust/Go adapters; a
  universal contract that anchors on Makefile/justfile/Task/Composer/CI `run:` lines with an explicit
  anchor-strength label. Discovery *invents nothing* — a tool named in a comment is not a declaration.
- **Inferring the KIND of work from the human's own words** (slice 1). Safe because kinds only ever
  **add** duties, never remove one: `TaskIdentity.kinds` is a union and a mislabel adds work. Widened
  narrowly to words that **assert brokenness** rather than merely name a topic — see Security risks.
- **Refusing a task at handoff when nothing could judge it** (slice 1). Strictly fail-closed: it
  refuses *earlier* than `finish` did, opens nothing, launches nothing, spends nothing.
- **Reporting whether the completion hook is actually installed** (slice 1). A state answer, not a
  verdict; it can only ever claim less.

**NOT safe — must stay human or operator:**

- **Auto-binding arbitrary prose requirements to arbitrary checks.** "Add email validation" bound to
  `npm test` would manufacture proof that does not exist. Which sealed check measures *which* stated
  requirement is a semantic judgement, and it is the operator's act by design.
- **Defaulting a kind when inference finds nothing.** A wrong kind adds a duty the change cannot
  discharge — a `bugfix` duty demands a base-vs-candidate discrimination, which a docs-only change
  cannot produce. That is a false *block*, and worse, it would be Canary inventing the authority to
  judge. Refusing and asking one question is the honest ending.
- **Closing a subjective duty.** Aesthetics and "feel" stay `canary accept`, in a terminal.

## WHAT STILL REQUIRES HUMAN JUDGMENT

1. **Which check measures a stated requirement** — the binding act. A wrong binding is fake proof.
2. **Subjective acceptance** — "does this look right", by construction, in a terminal.
3. **Waiving the discrimination rule** — when a change legitimately cannot be told from the base.
4. **Approving a project's hooks the first time** inside Claude Code (the harness's own consent gate).
5. **The first-time decision to protect a repository at all** (`canary setup`).

That is five decisions, and only the first two are recurring. Everything else Canary can answer.

## WHAT THE AGENT CURRENTLY DOES THAT CANARY SHOULD DO

Measured, on the stateful fixture, from the model's own exec operations:

- **~36 of 57 execs were the model re-running its own checks and tests** (`node --test-reporter=dot
  tests/contract-*.cjs` ×16, `node tests/contract-extra.cjs` ×11, `node checks/contract.cjs` ×4,
  `node run-tests.js` ×3, …). The plain arm ran **5 shell commands total**.
- **The model authored its own verification apparatus as whole-file writes** — `tests/contract-extra.cjs`
  ×3, `tests/contract-fuzz.cjs`, a `drive-tmp.cjs`, and a `tmp-mut` mutate/restore rig driven by 19
  `cmd /c` operations. Twelve tool-call lines carried 58,587 bytes of write payload (~37 % of the
  arm's text output).

This behaviour is **rational**: the model cannot otherwise know whether it is done. Canary should
absorb it by handing back a **short trusted verdict** instead: which check ran, its status, the first
failing assertion, the digest, and the path to the full log — the pattern the product already proves
works, since the Stop hook's failure payload is 308 characters where the block it replaced carried up
to 4,000.

**The constraint that governs this whole section, from this repository's own measurements:** the arm
that was told *not* to verify produced a **false done and a false green**. Suppressing the agent's
self-verification is the wrong lever. The replacement verdict must be **at least as informative and at
least as trusted** as what the agent produced for itself, or correctness is being traded for tokens —
which the priority order forbids.

## PROPOSED EVERYDAY WORKFLOW

```
once per repository:   canary setup --yes
thereafter:            use your coding agent normally
```

Target: **zero Canary commands typed by the human**, for ordinary objective work.

Canary is responsible for, invisibly: discovering the project and its checks; sealing the plan; wiring
the harness hook; isolating the change; running the sealed plan outside the model's context; promoting
only verified bytes; and telling the agent **one line** — `PASS`, or `FAIL: <short actionable
reason>`. The human is interrupted only for the two recurring judgements above.

Today the honest count is **three commands** (`setup`, `work`, `finish`) plus one human decision per
task that names no kind. The gap between three and zero is the agent-integration work, not a wording
change.

## PROPOSED EXPERT WORKFLOW

**Unchanged, deliberately.** `task` / `bind --reseal` / `isolate` / `isolate --verify` /
`isolate --promote` / `accept` / `provider …` remain the trust boundary and keep their vocabulary,
their exit codes and their `--json` envelopes. Everyday mode is a *presentation and orchestration*
layer over them — it must never be a second implementation of a gate, because two implementations is
two places for a gate to be weakened.

New in v1.3: `--verbose` becomes the door to the machinery, and every everyday refusal names the
expert command that resolves it.

## CLAUDE CODE INTEGRATION PLAN

**What exists:** one `Stop` hook written into `.claude/settings.json` (`node "<cli>" checkpoint`),
added by merge, never overwriting; backed up before writing; atomic; exactly removable by
`canary uninstall`. It can block a completion **once**, and it fails *open with an honest message*
(never a fake green) when the config is corrupt, distrusted or the plan is empty.

**Plan, in order of leverage:**

- **A. Keep the completion gate.** It is the only mechanism that can *refuse* today, and Cursor can
  inherit it (below).
- **B. Give the agent a verification TOOL, not a lecture.** **DONE in slice 2** — `canary setup` now
  registers `canary mcp` in the project's `.mcp.json`, so the agent can call `canary_doctor` and get
  Canary's verdict instead of authoring its own verification campaign. This is the single change that
  removes the ~36 self-run checks and their whole-file test apparatus from the model's context. The
  measured analogue in this repository's own corpus: arms that removed the model's check-running
  measured **−31.8 %** and **−58.5 %** tokens with correctness unchanged. The win is **projected, not
  measured** — whether the agent uses the tool rather than its own tests is a model-choice question and
  must be measured, not assumed (v1.2's optional-batch experiment failed by assuming exactly that).
- **C. Productise the confined transport.** The confinement already exists and is measured
  (`provider model-transport`: `--bare --restricted --tools '' --strict-mcp-config --setting-sources ''`,
  one tool, AppContainer + restricted token + zero capabilities + low integrity, with a broker that
  authenticates the caller by measuring its kernel token). It is today an 8–9 step operator ritual
  ending in a batch run from a prompt file. The product gap is **one command** that starts the agent
  under it.
- **D. Do not claim more than is true.** Claude Code's native tools cannot be removed by an MCP server,
  so on the default path the writes are unconfined. The `model CLI process itself` is not confined
  either — only its tool calls cross the boundary — and the existing probe measures the *advertised*
  tool list, not that the CLI cannot act natively. Both facts belong in the docs, and `HARDENED` stays
  unreachable until the measured deployment exists.

## CURSOR INTEGRATION PLAN

Researched from Cursor's own documentation. **The premise "Cursor offers only MCP" is out of date**,
and one finding changes the plan:

- **MCP servers are supported** (stdio/SSE/HTTP; `.cursor/mcp.json` + `~/.cursor/mcp.json`; one-click
  install; an extension API registers them without touching config).
- **No documented way exists to remove Cursor's native tools in the IDE.** Native edits are explicitly
  ungated — Cursor states agents "can modify workspace files without approval". So an MCP tool surface
  would be **additive**, and **MCP-only confinement is not achievable in Cursor today**. Only the SDK's
  `tools`/`disallowedTools` can switch built-ins off, and it is local-only and drives the loop from
  Canary's own process.
- **Cursor imports Claude Code hooks**, including `Stop` → `stop`, and honours a flat
  `{"decision":"block","reason"}` as an automatic follow-up. Third-party hook import is **on by
  default**. That makes the existing `canary setup` hook a plausible **zero-new-code completion gate
  for Cursor.**

**Plan:**

1. **Claim nothing until it is measured on a real Cursor install.** Two unknowns decide whether the
   import is actually a gate: Cursor's `stop` input is documented as `{status, loop_count}` while
   Canary derives the repo from `input.cwd` and keys its one-repair guard on `stop_hook_active`
   — whether Cursor synthesises those fields for imported Claude hooks is **undocumented**; and the
   default `loop_limit` for Claude-format hooks is `null` (no cap), so a mis-mapped guard could loop
   instead of stopping. Measure, then document.
2. **Teach `setup` to recognise Cursor.** Today it does not, and on a machine with `~/.claude` present
   it will report the Claude Code integration even when the user's agent is Cursor.
3. **If a real edit gate is wanted later**, the documented primitive is narrow: a Cursor Plugin
   (marketplace-installable, no hand-edited config) shipping a `preToolUse` hook on `Write`/`Shell`
   with `failClosed: true` and BOM-tolerant stdin parsing. That is a **permission gate on writes, not
   confinement** — Canary cannot put Cursor's native tools inside the AppContainer.
4. **Never claim HARDENED on any Cursor path.**
5. **Do not build a Cursor-specific architecture.** Cursor is the second consumer of one engine
   (`result`/`doctor`/`work`/`finish` over MCP), not a second engine.

## TOKEN ARCHITECTURE PLAN

Ranked by measured size of the mechanism it attacks. All win figures are **arithmetic projections**
from the measured totals — estimates, not measurements.

| # | Change | Attacks | Est. win | Trust cost |
|---|---|---|---|---|
| 1 | **An `edit`/`patch` primitive** (anchored replace or line-range), so a change is a patch and not a whole file body in the assistant message | #1 (70 %) | **≈ −35 %** on the dominant cell | A **new mutation authority inside the boundary**; needs the full escape battery re-run |
| 2 | **A trusted, compact "what do the project's own checks say" operation**, returning `{check, status, firstFailingAssertion, digest, logPath}` | #3 and its cause | **≈ −30 to −45 %** | Must be **broker-produced**, provenance-carrying, never model-writable, and must not read as "stop working" |
| 3 | **Short structured verdicts + digests instead of raw payloads** (`exec` → status/bytes/sha256/first failure line/artifact id; full log retrievable by explicit expand) | #2 (22 %) | **≈ −18 %** | Truncation can hide the failing assertion; digests must be computed **inside** the boundary; the artifact store is a new trusted path the worker must not write |
| 4 | **Cap and summarise `exec` output** deterministically (head + tail + elided count + digest + log path) | #2 | ≈ −7 % | Bounded: always keep exit status, first failing line, and a retrievable full log |
| 5 | **Compound `edit+check`** as one operation, collapsing write→run→read→decide into one decision | #3 | not projected | Low — same authority plus a check invocation |

**Two rules from the data that constrain every row above:**

- **Batching quantity is not the lever.** bug-sum won −61.5 % at 2.14 ops/call; bound-requirements won
  −83.9 % at 4.00 ops/call; stateful-replay **lost 175 % at 4.67 ops/call** — the most-batched cell is
  the worst cell.
- **The winning lever is content, not turns alone**: stop putting whole file bodies and unbounded
  command output into the model's own message history, and remove the *reason* the model runs its own
  verification campaign.

**Measurement hygiene, without which none of the above can be believed** (all cheap, all required
before a v1.3 token claim): run the plain arm **paired in the same session** instead of reading
another day's record; record the plain baseline path inside the pilot record (the current default path
does not exist on disk); archive transport logs per run (the pilot overwrites one temp filename);
n ≥ 3 per Canary cell (every Canary cell today is a single trial); store the prompt **actually sent**;
and log a per-request context size from the provider side, since the CLI's per-message usage is
partial and the trajectory is currently unmeasurable.

**Standing target:** ≤ 75 % of plain on a representative executable benchmark. On the evidence
above, reaching it requires rows 1 and 2 — the two changes that remove content from the model's
context. Nothing in the recorded data suggests prompt wording can get there.

### MEASURED UPDATE — row 1 is implemented, and the target's binding term is NOT what this table implies

`edit` was built and measured (`tooling/benchmark/results/v13p1-edit-primitive-measurement.md`). Three
findings, all from executed runs, and one of them changes the plan:

1. **The mechanism works.** A representative change costs **141 B as an `edit` versus 1815 B as a
   `write` — 8 %** — measured through the real AppContainer, with containment proven unchanged
   (absolute path, traversal and the sealed authority are all denied, victims byte-unchanged) and
   ambiguous anchors refused rather than guessed.
2. **The model chooses it** — which was the open question, because this repository has already made the
   opposite mistake once (an optional `batch` primitive used zero times in 50 calls). On a small real
   task through the real confined transport: `{"list":2,"read":3,"edit":1,"exec":3}` — **edit 1,
   write 0**, 616 bytes of its own output for a 2,499 B source file, defect fixed and confirmed from the
   trusted side.
3. **It is not sufficient, and the table above now looks wrong.** On the stateful stress test the
   model's own output fell **39,351 → 30,504 (−22.5 %)** — exactly the term row 1 attacks — and the
   TOTAL did not improve: **595,419 vs v1.2's 585,337 (+1.7 %, i.e. noise)**, against plain's 212,777.
   Correctness held at 406/406 both sides.

The reason is in the same table: **cache-read is 87 % of the total and is driven by `turns ×
accumulated context`.** Turns went 22 → 24, so a 22 % smaller turn was cancelled by two more turns.
**The binding term is turn count, not bytes per write.** Rows that reduce bytes (this one, and the
output cap in row 4) cannot reach the target alone; rows that reduce TURNS (2 and 5) are the ones that
can. And even the adoption is task-shaped: on the long run the model still issued **10 whole-file
`write`s against 4 `edit`s**, because it regenerates files it is still designing — so the next step is
to make the compact form the ONLY form for changing an existing file, not merely the cheaper one.

**Nothing about the token target is claimed as achieved.** The honest sentence is: *output per turn fell
22.5 %; the total did not move.*

   check you have just run") is now shipped through Canary's own two agent channels (`canary mcp`'s
   initialize instructions and the advisory `AGENTS.md` block), with the RELIABILITY half kept because
   the aggressive variant that forbade self-verification measured a false done **and** a false green.
2. **The ceremony is what costs.** `work` → `finish` is **+77.8 %** — nearly twice the everyday shape —
   *with identical correctness*. So v1.3's zero-ceremony goal and its token goal are the same goal, and
   `work`/`finish` are confirmed as an EXPERT surface rather than the ordinary path.
3. **The long task does not explode on the everyday shape** (17 turns, 96.1 % of plain). The explosion
   belongs to the transport configuration, not to "Canary on a long task".

**≤75 % is still not met by any recorded configuration**, and the honest claim is the measured one:
Canary's everyday shape costs about the same as working without it while catching work a green suite
cannot discriminate; its confined transport makes short tasks 2–6× cheaper and long ones more expensive.

### MEASURED UPDATE 3 — the `plain` arm was NOT wired, and Canary's per-turn footprint cannot reach the target

**Correction first, because MEASURED UPDATE 2 above states the opposite.** This audit claimed
"`canary setup --yes` runs for **every** arm (`run-trial.mjs:255`), so Canary is wired in all of them and
`plain` vs `guarded` differ by one paragraph of instruction". That is **false**. The setup block is
guarded by `run-trial.mjs:254` —

```js
if (arm === 'canary' || arm === 'workflow' || arm === 'invisible' || arm === 'guarded') {
```

— which `plain` is not in, and the harness says so again at line 803 ("the plain arm HAS no Canary").
`plain` gets no seal, no Stop hook and no MCP entry.

The correction **strengthens** the headline rather than weakening it: 92.7 % is not "two Canary
configurations differing by a prompt paragraph", it is **Canary's everyday shape against genuinely not
using Canary at all** — which is the comparison criterion (4) actually asks for. It also means the
`plain` arm was never gated, so "no false done in any arm" cannot be explained by the gate being present
everywhere.

**Second measurement — what Canary costs on every turn, used or not** (`tooling/probes/v13-standing-context.mjs`).
MCP instructions and tool definitions are advertised at handshake and re-sent on every request, and in the
recorded ledgers the dominant term is cache-read of accumulated context, so a standing byte is paid once
*per turn*. Measured from the real server over the real transport:

| | bytes |
|---|---|
| instructions | 1,475 |
| tool definitions (6 tools) | 4,251 |
| **standing payload, per turn** | **5,726** |
| of which the expert ceremony (`canary_work` 1,139 + `canary_finish` 784) | 1,923 = 33.6 % |

At ~1,432 tokens/turn (bytes ÷ 4 — a derived figure, not a measurement) and 17 turns, that is ≈24,300
token-equivalents ≈ **6 % of the 379,792-token everyday arm**. Removing the entire ceremony would return
about 2 points. **So ≤75 % is not reachable by trimming Canary's own footprint**, and this audit will not
claim otherwise: the remaining ~17 points would have to come from the agent doing materially less work,
which the arm map bounds at what self-verification Canary actually removes.

**One consequence worth stating plainly:** `run-trial.mjs` launches the agent with `--strict-mcp-config`
and **no** `--mcp-config`, so the fixture's own `.mcp.json` never loads and the measured canary arms are the
**Stop-hook-only** shape. The plain-vs-guarded *comparison* stays fair (neither arm loads an MCP server),
but the 92.7 % figure does not include the 5,726 B above, so the real everyday footprint is somewhat worse
than the measured ratio. Recorded as an OPEN finding, not asserted — closing it is a harness decision.

**Third measurement — the one harness step Canary cannot close** (`tooling/probes/v13-mcp-consent.mjs`).
`setup` registers the MCP server; Claude Code holds a project-scoped server at `⏸ Pending approval` until a
human approves it once. Four candidate settings forms were tried (project and local scope ×
`enabledMcpjsonServers: ["canary"]` and `enableAllProjectMcpServers: true`) and read back through two
independent views (`claude mcp list` and `claude mcp get canary`). **All four produced byte-identical
output** — scope `Project config (shared via .mcp.json)`, status `⏸ Pending approval`. The gate is not
reachable from the settings files Canary writes on this harness version.

That the broad key did **not** work is the good outcome for trust: had only `enableAllProjectMcpServers`
flipped the state, it would have approved every server in `.mcp.json` — including one nobody at Canary
inspected — and Canary must never vouch for software it did not measure. `setup` therefore does the only
honest thing available and **names the step** (`onboarding.ts:2416`), guarded by `if (!integrable) … return 2`
so a non-Claude-Code harness never sees Claude-specific advice. Confirming that note is *necessary* rather
than a workaround is what this measurement adds.

## EXPECTED COMPLEXITY REDUCTION

**Honest position: the first slice does not reduce code, and the plan's complexity reduction is not yet
earned.** What the slice does is remove a *dead end* and a *false claim*; what it adds is ~90 lines of
product code and no new subsystem.

What the plan must actually buy, in order:

1. **Everyday surface: 3 commands → 1.** `work` and `finish` move behind the agent's tool surface; the
   human types `setup` once. This is a *deletion* of user-facing surface, not an addition.
2. **Human decisions per task: 1 → 0** for tasks whose prose names their kind (measured: 3 of 4
   wordings now complete with no declaration at all; the fourth refuses before spending anything).
3. **Vocabulary: MEASURED, and it is already most of the way there — so this item is closed rather
   than rewritten.** `tooling/probes/v13-everyday-vocabulary.mjs` counts the internals the ordinary
   path speaks: **13 occurrences of 5 distinct terms** — `status` 7 (`sealed` ×2, `seal` ×2,
   `authority` ×2, `candidate` ×1), `doctor` 1 (`obligation`), and the completion gate 5
   (`sealed` ×2, `seal` ×2, `obligation` ×1). **`setup` and `agents` speak none.** The gate's message
   is the one the AGENT reads, and apart from those five words it is plain, actionable English:
   *"the checks pass on the base commit too, so they carry no evidence about this change … needs a
   check that FAILS without the change and passes with it."* The first draft of this audit expected a
   twelve-term vocabulary to be replaced; the measurement says the reduction is already substantially
   true, and the brief is explicit that renaming internals for cosmetics is not the work — so the
   finding is recorded and pinned as a **ratchet** (the probe fails if the ordinary path gets louder)
   rather than churned. The same probe checks the other direction, so the default cannot be made
   quieter by deleting what `--verbose` explains.
4. **No new subsystem.** The engine stays one engine: the verification core, the candidate/promotion
   primitives and the confinement are unchanged; integrations are thin adapters over
   `result`/`doctor`/`work`/`finish`.

**Explicitly rejected as complexity for too little benefit:** a second lifecycle for Cursor; a
per-agent architecture; auto-binding heuristics; any "smarter" default that invents an obligation.

## SECURITY RISKS

**Introduced by the first slice, and why each is bounded:**

| Change | Risk | Bound |
|---|---|---|
| Widened `inferTaskKinds` | A mislabel adds a duty the change cannot discharge → a **false block** | Kinds are a **union**: a mislabel can only *add* obligations, never remove one. The words added **assert brokenness** (`wrong`, `incorrect`, `failing`, `misbehav*`, "does not work") rather than name a topic; a test pins that `add error handling to the parser` still infers **nothing**. Direction of error is toward more verification, never less. |
| `work` refuses when no authority is frozen | Could refuse a task that would have completed | It cannot: the frozen kind set is exactly the authority `candidate.ts:602-609` requires, so such a candidate is **always** refused at `finish`. The gate moves discovery from after the spend to before it — 0 candidates opened, 0 worker launches, 0 tokens. |
| `agents` reports wiring, not detection | Could under-report protection | It reports the same fact `status` and `readOnlyProblems` already compute from the config and settings files. Strictly *less* claiming; the failure mode is conservatism. |
| `finish` names the real recovery for `task-authority` | None | Presentation only; no gate, verdict, exit code or envelope changes. |

**Preserved, verified by the existing batteries:** the worker cannot self-bind, cannot seal its own
authority, has no unrestricted fallback, and cannot promote itself; verification authority stays
frozen at isolation; `HARDENED` remains reachable only from a measured deployment. The escape battery,
the alias-lifecycle audit, the production attack battery and the pre-bound end-to-end workflow are all
re-run against the changed bytes before any claim — see the verification record at the end of this
document.

**Residual risks that are NOT fixed and must not be implied away:**

1. **An agent with shell access can re-seal.** `canary setup` has no TTY gate (only `accept` does), so
   an agent can clear a drift block by re-running setup. The discrimination obligation still blocks a
   weakened suite, but the drift *gate* is not agent-proof. Open, documented, unchanged by this slice.
2. **On the default path the agent's writes are unconfined, and the change is never isolated.** The
   *verdict* risk is covered — a change the sealed checks cannot discriminate is blocked (measured,
   section F2) — so this is a lifecycle gap, not an acceptance hole. It is nonetheless the reason the
   everyday path cannot promise "the bytes that passed are the bytes you have".
3. **The model CLI process is not confined**; only its tool calls cross the boundary, and the existing
   probe measures the *advertised* tool list rather than the CLI's inability to act natively.
4. **Same-UID forgery, no network egress control and no filesystem jail** remain the documented LOCAL
   ceiling. Nothing in this audit narrows or widens them.

## FIRST IMPLEMENTATION SLICE

**"The ordinary path either works, or says so before spending anything — and Canary never claims
protection it does not have."**

Chosen because it is the smallest change that (a) fixes a measured trust defect, (b) removes the
dead end in the exact path v1.3 must make work, and (c) adds no subsystem. Four changes, three files:

1. **`apps/cli/src/onboarding.ts` — `inferTaskKinds`.** Added the ordinary ways a developer *asserts*
   brokenness. Justified by this repository's own benchmark fixture: `bug-sum`'s task statement
   ("*…a test suite (npm test) that is currently failing.*") previously inferred **nothing**, so the
   corpus's most ordinary task was a guaranteed dead end.
2. **`apps/cli/src/orchestrate.ts` — `cmdWork`.** Refuses, before isolation, when the registered task
   freezes no authority: prints `CANNOT BE JUDGED`, opens no candidate, launches no worker, and names
   the one thing the human must supply.
3. **`apps/cli/src/onboarding.ts` — `agentCapability` + `gatingHookInstalled` + `cmdAgents`.** "Detected"
   and "protected" are now different answers; `hooked` means the hook is installed in *this*
   repository, and the verdict is decided by wiring. `apps/cli/src/protocol.ts`'s doc comment was
   corrected to match.
4. **`apps/cli/src/candidate.ts` — the refusal's `next:` lines.** `task-authority` is no longer
   classified as worker-closable, and its recovery (re-register with a kind, open a fresh candidate)
   is stated plainly first.

**Measured result** (`node tooling/probes/v13-journey-baseline.mjs`, **15/15 observations held**, exit 0,
1 recorded open finding):

| fixture | before | after |
|---|---|---|
| intent matching no keyword | `work` exit 0 → candidate opened → correct fix refused at `finish` (exit 2) | `work` exit 2, **candidate not opened**, refusal names `--kind` |
| same intent + `--kind bugfix` | completed | completed (unchanged) |
| intent containing "fix" | completed | completed (unchanged) |
| **`bug-sum`'s own task statement** | **nothing inferred → dead end** | `bugfix` inferred → **completes, exit 0, bytes promoted** |
| `.claude/` present, no hook | `agents` → `CONNECTED`, exit 0 | `agents` → `NEEDS ATTENTION`, `hook NOT installed here`, exit 2 — **agrees with `status`** |

The benchmark harness's own classification is unaffected: `v12-workflow-preflight.mjs` still reports
`bug-sum` as `A-executable` — and that label is now *true*, where before it described a candidate that
`finish` would have refused.

**The `OPEN` finding this slice leaves behind** is the everyday path's missing lifecycle — no
isolation and no frozen task authority (section F, and the correction above). It is recorded, not
asserted, and it is deliberately not a red: it is a gap in *when* Canary acts, not in what it accepts,
and the probe proves the acceptance question is already closed.

## SECOND SLICE — the agent can ASK, instead of guessing

**"`setup` registers Canary's tools, so the agent stops running its own verification campaign."**

Chosen because the correction above moved the target: the acceptance question is already closed on the
everyday path, but the gate only speaks at the **end**. So the agent cannot ask *"am I done?"*, and it
does the only thing it can — it verifies itself. Measured on the long fixture: **~36 of 57 confined
execs were the model re-running its own checks**, plus a self-authored fuzz/mutation rig written as
whole-file payloads (58,587 B). That behaviour is rational, and it is ~70 % of that arm's token cost.
Removing the *motive* is the lever; forbidding the behaviour is contradicted by this repository's own
measurements (the arm told not to verify produced a false done and a false green).

**What was already there.** `canary mcp` — a stdio MCP server that exposes exactly six thin argv
templates over commands the CLI already had (`result`, `status`, `agents`, `doctor`, `work`, `finish`),
deliberately **not** exposing `accept` (that is a human act in a terminal). It grants no authority: it
can only *request* operations, and every one of them is judged by the same gates. The missing piece was
that a user had to discover and configure an MCP client by hand.

**What this slice adds** — `apps/cli/src/onboarding.ts`: `installMcpServer`, `hasMcpEntry`,
`pruneOwnedMcp`, wired into `setup` beside the Stop hook, with the same discipline that file already
had for `settings.json`: parse before writing, refuse to write through a link, back up the previous
bytes, prune only entries this installation wrote, write atomically, and record what was touched so
`uninstall` can undo exactly that. Ownership is the **argv signature**, never the key name.

**The regression that mattered most** is not the server: it is that `setup` now writes a second file
into the user's repository. `isCanaryOwnArtifact` had to learn about `.mcp.json`, or the freshly written
file would count as *the change*, the sealed checks would be green on the base too, and **every
repository would report NOT PROVEN the moment it was wired** — the verifier's own file mistaken for the
author's work. Section G3 of the probe asserts that this does not happen.

**Measured result** (`tooling/probes/v13-journey-baseline.mjs` §G, **24/24 observations held**, exit 0):

| property | measured |
|---|---|
| G1 | `setup` writes one entry running this Canary as an MCP server |
| G2 | a stranger's server entry is preserved byte-for-byte |
| G3 | **the newly written file does not make the repo look changed** — `status` stays CONNECTED |
| G4 | the completion gate still allows a wired repo with no change |
| G5 | re-running `setup` is byte-identical (324 bytes before and after) |
| G6 | a foreign server under our key is **refused, not replaced**, and the file is unchanged |
| G7 | a real `initialize` + `tools/list` handshake returns `serverInfo.name = canary` and exactly 6 tools |
| G8 | `accept` is not among them |
| G9 | `uninstall` removes exactly our entry and keeps the stranger's |

Plus `apps/cli/test/mcp-wiring.test.ts` (9 cases) so the merge/refuse/prune semantics are protected by
`npm test`. **That test caught a real bug before it shipped:** pruning our only entry deletes the
`mcpServers` object itself, so a reference taken before the prune wrote the new entry into a detached
object — a re-run produced a file with *no servers at all*. The fix re-acquires the map after pruning.

**And the battery caught a second, worse one — this is the part worth reading.** Teaching `setup` to
write a third file broke `canary bind --reseal` for every user: `--reseal` commits the declaration
alone and *refuses when any other path is dirty*, and the freshly written `.mcp.json` counted as
"another change". The operator would have been told their working tree held changes Canary itself had
just made, with no fix available. `verify:productization` reported it precisely —
**`FAIL 1.2 REQUIREMENT UNBOUND gate (no worker is handed a duty it cannot close)`, 82 of 83 steps
green** — and nothing else in the suite noticed.

The repair is structural, not a patch: the excluded set was a hard-coded settings path, and is now
read from `cfg.touched` — the same list `setup` records, excludes from its baseline, and `uninstall`
prunes — so it stays correct as the managed surface grows. The probe that caught it was making the
same mistake from the other side (a hard-coded list of "Canary's own paths"), so it now derives the
set from the config too: **a probe that must be edited whenever the product changes is a probe that
will eventually be edited in the wrong direction.** The property that actually matters — that
`--reseal` sweeps no unrelated work into the commit — is asserted separately, on the commit's own
contents, and was never in question.

**Honest limits of this slice:**

- **It is not "seamless" yet, and must not be described as such.** Claude Code's own consent gate for
  project-scoped MCP servers still applies; Canary writes the entry, the harness decides whether to
  honour it. This removes a *configuration* step, not the harness's approval.
- **It does not confine anything.** The agent's native tools remain available and remain the executor;
  the tools added are Canary's read/verify/lifecycle operations.
- **The token win is projected, not measured.** The mechanism is measured (the self-verification
  campaign is real and costs ~70 % of that arm); whether an agent *uses* the tool instead of running
  tests is exactly the "model tool choice" question that v1.2's optional-batch experiment got wrong by
  assuming. It must be measured, not asserted.
- **`setup`'s output now names the file it wrote** — a file Canary adds to someone's repository must
  never appear unexplained.
